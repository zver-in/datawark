# PRD-001: DataWark: AI Data Gateway

**Статус:** Draft  
**Версия:** 0.1  
**Тип:** Product Requirements Document  
**Продукт:** Open-source, self-hosted AI Data Gateway  
**Основной язык реализации:** Go  
**Дата:** 11 ноября 2026 года

## 1. Краткое описание

**DataWark** — open-source сервис, предоставляющий AI-агентам, приложениям и пользователям управляемый доступ к структурированным данным. Gateway принимает запросы через REST API или MCP, определяет права вызывающего субъекта и выполняет только операции, разрешённые декларативными политиками доступа.

Принцип продукта: **LLM может предложить запрос, но не может назначить себе права или обойти проверку Gateway.** Политики применяются сервером независимо от промптов; дополнительную защиту обеспечивают минимальные привилегии на стороне СУБД.

Первый релиз ориентирован на PostgreSQL, безопасное чтение, политики уровня таблиц и колонок, ограниченный структурированный язык запросов, аудит, REST API и MCP. Встроенный AI Database Assistant — следующее приложение поверх того же ядра, а не обязательный компонент Gateway.

## 2. Проблема

Прямое подключение LLM или AI-агента к базе данных создаёт риски:

- Модель может сгенерировать обращение к чувствительным или нерелевантным данным.
- Инструкции в промпте не являются надёжной границей авторизации.
- Права часто задаются слишком широко — например, доступом к целой базе вместо конкретных таблиц и колонок.
- Непрозрачно, кто, когда, через какого агента и по какой политике получил данные.
- Организациям сложно повторно использовать единые правила доступа для разных AI-клиентов.

Нужен самостоятельный слой между AI-клиентом и СУБД с проверяемой, тестируемой и наблюдаемой моделью доступа.

## 3. Цели и нецели

### 3.1 Цели

1. **Безопасное чтение по умолчанию:** разрешены только явно перечисленные ресурсы и операции.
2. **Policy-as-Code:** декларативные, версионируемые политики с валидацией и тестированием.
3. **Единый enforcement:** одинаковые ограничения для REST, MCP и будущего чата.
4. **Объяснимость:** понятные причины отказов и журнал решений авторизации.
5. **Простота внедрения:** один Go-сервис, PostgreSQL, конфигурация и Docker Compose.
6. **Расширяемость:** возможность добавлять адаптеры СУБД, схемы идентификации и AI-клиентов.

### 3.2 Не входит в MVP

- UPDATE, DELETE, INSERT, DDL и произвольное выполнение SQL.
- Поддержка MySQL, ClickHouse и других СУБД.
- Полноценный встроенный LLM-чат или обучение моделей.
- RAG по содержимому всей БД и хранение embeddings строк.
- Автоматическое создание SQL-прав пользователей в production без проверки администратора.
- Редактор политик в веб-интерфейсе, approval flows, маскирование чувствительных значений.
- Универсальные JOIN/CTE/подзапросы, произвольные SQL-функции.
- Полноценная многотенантная SaaS-инфраструктура.

## 4. Целевая аудитория и задачи

| Персона | Задача | Ценность |
|---|---|---|
| Backend / AI engineer | Подключить AI-агента к данным без выдачи широких DB credentials | Единый защищённый API |
| Platform / DevOps engineer | Настроить и версионировать разрешения для приложений | Policy-as-Code, аудит, self-hosted |
| Security engineer | Проверить, что агент не читает запретные поля | Deny-by-default, тесты политик, enforcement |
| Аналитик / внутренний пользователь | Получать ответы на вопросы о разрешённых данных | В будущем — AI Database Assistant |

### Основные Jobs-to-be-Done

- «Подключить AI-клиент к PostgreSQL и дать ему читать только `sales.orders` без email клиентов».
- «Разрешить агенту подсчитывать выручку, но запретить изменение данных».
- «Увидеть, почему конкретный запрос отклонён и какая версия политики сработала».
- «Подключить другого AI-ассистента, сохранив прежние правила доступа».

## 5. Продуктовые принципы

- **Deny by default:** отсутствие явного разрешения равно отказу.
- **Least privilege:** у Gateway и пользователей СУБД только необходимые привилегии.
- **Fail closed:** недоступность Policy Engine, некорректная политика или невозможность установить идентичность приводят к отказу.
- **No prompt-based security:** текст промпта не предоставляет и не расширяет права.
- **One policy path:** нельзя обойти проверку, выбрав другой протокол.
- **Explainable, not leaky:** авторизованным пользователям доступны причины отказа, но сообщение не раскрывает скрытые имена и данные.
- **Auditable:** каждый запрос связан с actor, policy version и результатом решения.

## 6. Пользовательские сценарии

### UC-01. Подключение базы

Администратор добавляет PostgreSQL connection через защищённую конфигурацию, использует отдельного DB-пользователя с read-only правами и запускает проверку доступности.

**Результат:** Gateway может обращаться только к подготовленному набору views/таблиц, доступному указанной DB-роли.

### UC-02. Создание политики

Администратор описывает роль `sales_analyst` и разрешает чтение `sales.orders` только из колонок `id`, `status`, `total`, `created_at`.

**Результат:** политика валидируется и получает версию. Все остальные таблицы и колонки закрыты.

### UC-03. Разрешённый запрос через REST или MCP

AI-клиент с идентичностью `analyst-agent` запрашивает агрегированную выручку за месяц.

**Результат:** запрос проверен, преобразован в параметризованный SQL, выполнен с лимитами и зарегистрирован в журнале.

### UC-04. Запрещённый запрос

AI-клиент пытается получить `customers.email` либо вызвать изменение данных.

**Результат:** Gateway отклоняет запрос до обращения к СУБД; событие отказа попадает в audit log.

### UC-05. Объяснение политики

Администратор запускает `policy explain` для роли и структурированного плана запроса.

**Результат:** система показывает решение `allow/deny`, идентификатор политики и причины, не выполняя SQL.

## 7. Scope и приоритеты

### P0 — обязательные требования MVP

| ID | Требование | Критерий приёмки |
|---|---|---|
| FR-01 | Подключение одного PostgreSQL datasource | Конфигурация без хранения пароля в политике; проверка соединения |
| FR-02 | Идентификация API-клиента | Каждый запрос сопоставлен с активным principal/role; неизвестные отклоняются |
| FR-03 | Policy-as-Code (YAML) | Схема валидируется; невалидная конфигурация не активируется |
| FR-04 | Allowlist таблиц/колонок и SELECT-only | Неописанные ресурсы, операции и выражения отклоняются |
| FR-05 | Ограниченный структурированный Query Plan | Поддержаны projection, filters, sort, limit, COUNT/SUM/AVG; без произвольного SQL |
| FR-06 | Безопасный SQL Compiler | Идентификаторы берутся из подтверждённой схемы; значения параметризуются |
| FR-07 | Единый enforcement для REST и MCP | Одинаковый план и principal дают одно и то же решение |
| FR-08 | Ограничения ресурсов | `maxRows`, `statement_timeout`, запрет множественных statement |
| FR-09 | Audit log | Пишутся actor, request ID, datasource, политика/версия, результат, длительность; чувствительные значения не пишутся по умолчанию |
| FR-10 | Policy explain и dry-run | Можно получить безопасное объяснение решения без выполнения запроса |
| FR-11 | Self-hosted развёртывание | Docker Compose, миграции метаданных, health/readiness endpoints |
| FR-12 | Защита schema discovery | Клиент видит только разрешённые объекты и поля |

**Ограничение MVP:** только одна таблица в запросе; JOIN и сложные выражения откладываются, чтобы не выпускать непроверенную SQL-авторизацию.

### P1 — следующий релиз

- Встроенный AI Database Assistant: natural language → структурированный Query Plan → подтверждённый результат.
- RAG только по разрешённым метаданным и документации схемы.
- Row-level restrictions и tenant isolation с проверяемым DB-enforcement.
- Дополнительные агрегаты, контролируемые JOIN и policy tests в CI.
- OIDC/SSO, роли пользователей, улучшенная observability.

### P2 — развитие платформы

- MySQL и другие адаптеры, masking, approval workflow для writes.
- Централизованное управление версиями политик, multi-instance deployment.
- Политики для RAG-индексов, аналитика и quality evaluation Text-to-SQL.

## 8. Предлагаемый пользовательский API

### REST

- `POST /v1/query` — выполнение структурированного запроса.
- `POST /v1/query/explain` — предварительная проверка разрешения и формы запроса.
- `GET /v1/schema` — только разрешённая часть схемы.
- `GET /v1/health`, `GET /v1/ready` — эксплуатационные проверки.
- `GET /v1/audit` — административный доступ к истории решений (не публичный endpoint).

**Пример запроса:**

```json
{
  "datasource": "analytics",
  "query": {
    "table": "sales.orders",
    "select": ["status"],
    "aggregates": [{"function": "sum", "column": "total", "as": "revenue"}],
    "filters": [{"column": "created_at", "operator": "gte", "value": "2026-09-01"}],
    "groupBy": ["status"],
    "limit": 50
  }
}
```

**Пример ответа при отказе:**

```json
{
  "error": {
    "code": "POLICY_DENIED",
    "message": "Запрос не разрешён для текущей роли",
    "requestId": "req_01"
  }
}
```

Подробный `policy explain` доступен только уполномоченному администратору. Тексты и коды ошибок не должны раскрывать существование недоступных ресурсов обычным клиентам.

### MCP

На старте поддерживаются инструменты `list_allowed_schema`, `query_data`, `explain_query`. Все используют тот же сервис авторизации и компиляции запросов, что REST; MCP не получает отдельного пути к БД.

## 9. Пример политики

```yaml
apiVersion: gateway.dev/v1alpha1
kind: AccessPolicy
metadata:
  name: sales-analyst
  version: 1
spec:
  principals:
    roles: [sales_analyst]
  datasource: analytics
  allow:
    - table: sales.orders
      operations: [select]
      columns: [id, status, total, created_at]
      aggregates: [count, sum, avg]
  limits:
    maxRows: 100
    timeout: 3s
```

Семантика: разрешение применимо только к перечисленным полям и операциям; все отсутствующие ресурсы запрещены. `version` и названия полей — предварительный дизайн DSL, подлежащий фиксации в техническом RFC.

## 10. Требования безопасности

1. **Слой БД:** отдельная роль без write/DDL privileges, без ownership/BYPASSRLS; при необходимости — строго ограниченные views и PostgreSQL RLS.
2. **Слой Gateway:** structured Query Plan → проверка AST/семантики → policy decision → безопасная компиляция → выполнение. Никакой конкатенации пользовательских значений в SQL.
3. **Схема и метаданные:** возвращать только разрешённые таблицы/колонки; не предоставлять AI полную схему «для удобства».
4. **Изоляция идентичности:** роли и claims поступают из проверенной аутентификации, а не из клиентского JSON или промпта.
5. **Отказы и лимиты:** недопустимые операции, сложные конструкции, невалидные фильтры и превышение лимитов отклоняются.
6. **Аудит и секреты:** секреты находятся вне репозитория и политик; журнал не хранит сырые результаты запросов и чувствительные параметры по умолчанию.
7. **Defense in depth:** политика приложения не заменяет права СУБД; даже ошибка Gateway должна иметь ограниченный радиус воздействия.
8. **Prompt injection:** содержимое БД и результаты RAG считаются данными, а не управляющими инструкциями.

**Важное ограничение:** проверка таблиц и колонок не предотвращает все утечки через агрегаты, маленькие группы, косвенные выводы и последовательность запросов. Для чувствительных сценариев потребуются отдельные правила агрегирования, пороги групп и ограничения частоты запросов; в MVP такие сценарии исключаются из поддерживаемых.

## 11. Логическая архитектура

```text
REST Clients / MCP Clients / Future DB Assistant
                    |
             AuthN + Identity
                    |
            Query API / Schema API
                    |
          Policy Resolver + Evaluator
                    |
            Query Plan Validator
                    |
             SQL Compiler
                    |
           Execution + Limits
                    |
             PostgreSQL

     Audit & Observability across all stages
```

Система разрабатывается как **модульный Go-монолит** с независимыми интерфейсами для источников данных, policy evaluation, query planning и аудита. LLM не входит в доверенную зону исполнения и не имеет собственных DB credentials.

## 12. Нефункциональные требования

| ID | Требование | Целевой критерий |
|---|---|---|
| NFR-01 | Предсказуемая авторизация | 100% негативных security test cases получают отказ |
| NFR-02 | Управляемая задержка | p95 накладных расходов Gateway ≤ 100 мс на тестовом стенде, без времени самой БД и LLM; целевой ориентир, не SLA |
| NFR-03 | Наблюдаемость | Метрики количества запросов, отказов, ошибок и длительности; request IDs |
| NFR-04 | Отказоустойчивость | При ошибке policy/backend сервис не расширяет разрешения |
| NFR-05 | Тестируемость | Unit, integration и property/fuzz tests для компилятора и политик |
| NFR-06 | Совместимость | Версионируемые REST API и YAML DSL; миграционный путь при изменениях |
| NFR-07 | Развёртывание | Локальный запуск через Docker Compose, инструкция для Kubernetes позже |

## 13. Критерии готовности MVP (Definition of Done)

- Разработчик поднимает Gateway и тестовую PostgreSQL в Docker Compose.
- Администратор создаёт read-only DB роль и активирует проверенную YAML-политику.
- Клиент вызывает один и тот же разрешённый запрос через REST и MCP и получает согласованный результат.
- Попытки прочитать запрещённую таблицу/колонку, отправить write-операцию или обойти правила через вложенный/неподдерживаемый запрос отклоняются **до выполнения**.
- Неавторизованный клиент не получает список скрытых таблиц.
- При некорректной политике, неизвестном principal и ошибке policy evaluation доступ не предоставляется.
- `query explain` показывает решение, `audit` фиксирует его с указанием версии политики.
- Интеграционные тесты подтверждают соблюдение лимитов, DB grants и защиту от SQL injection.
- В репозитории есть README, quickstart, пример политики, архитектурное описание и security policy.

## 14. Метрики успеха

### Продуктовые

- Время от клонирования репозитория до первого разрешённого запроса (цель для quickstart: ≤ 15 минут).
- Доля пользователей, прошедших quickstart без ручной помощи.
- Число реальных интеграций REST/MCP, активных участников и issue/PR от сообщества.

### Качество и безопасность

- Доля security regression tests, завершившихся успешно: 100% как release gate.
- Число критических непроверенных обходов политики: 0 перед релизом.
- Latency overhead, количество ошибочных отказов, частота `POLICY_DENIED` и runtime ошибок.

Эти значения — продуктовые цели и gates, а не подтверждённые показатели системы.

## 15. Риски и способы снижения

| Риск | Последствие | Мера |
|---|---|---|
| Ошибка SQL authorizer | Чтение закрытых данных | Ограниченный query DSL, DB grants/views, fuzzing, негативные тесты |
| Prompt injection | Попытка выполнить запрещённое действие | Отсутствие прямого DB-доступа у LLM; enforcement вне модели |
| Утечки через агрегаты | Восстановление частных значений | Ограничить MVP несекретной аналитикой; затем thresholds и anti-inference меры |
| Неправильная DB-конфигурация | Избыточные реальные привилегии | Preflight проверки роли, отказ при явно опасной конфигурации, рекомендации по views |
| Слишком широкий MVP | Долгая разработка и сложная безопасность | PostgreSQL-only, SELECT-only, один table source, без свободного SQL |
| Конкуренция с MCP-серверами | Нечёткая ценность | Позиционировать продукт вокруг testable policy enforcement и explainability |
| Утечки через логи | Раскрытие данных из query/result | Redaction и metadata-only audit по умолчанию |

## 17. Открытые вопросы

1. Как хранить политики в v1: только файлы GitOps или также административный API?
2. Достаточно ли API keys для MVP или стоит сразу поддержать OIDC/JWT?
3. Нужна ли базовая row-level фильтрация в MVP или только в P1 после проработки DB enforcement?
4. Какие агрегирующие функции разрешены и как ограничить косвенное извлечение чувствительной информации?
5. Должны ли политики объединяться по принципу union разрешений или требовать явного приоритета deny?
6. Какую модель публикации политик выбрать: atomic reload с immutable snapshot или версия в отдельном registry?
7. Предлагать ли встроенный чат в первом публичном демо или ограничиться подключением внешнего MCP-клиента?

## 18. Решение, рекомендуемое для старта

**Строить AI Data Gateway как самостоятельный policy-enforced data access layer; AI Database Assistant развивать как первый клиент поверх него.**

Публичное обещание v0.1: *«Дайте AI-агенту доступ только к разрешённым данным PostgreSQL, с декларативными политиками, аудитом и одинаковой защитой через REST и MCP».*

Первый релиз не должен заявлять поддержку произвольного SQL, row-level security «из коробки» для любых схем или невозможность всех косвенных утечек. Эти ограничения должны быть явно описаны в документации и threat model.
